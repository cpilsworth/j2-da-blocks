J2 Hotels · Data Integration · Edge Delivery Services

From a POST‑locked API to publishable content.

How a single category of ~450 hotels went from un‑addressable search results to data we can link to, embed live, and publish as pages.

The original site & its limits A GET‑addressable JSON API Server‑rendered HTML JSON→HTML publishing to EDS

01 · Where we started

The hotel list lived behind a POST request.

The existing J2 site fetched its filtered hotel results by sending a POST body to the booking API — all the filters (resorts, star ratings, board basis, sort order, page) travelled inside the request body.

REQUEST

POST  /getfilteredhotels

{
  "predefinedResorts": [573, 575],
  "starRatings": [4, 5],
  "hotelOrder": "1",
  "page": 0
}

Works fine for an in‑page search widget. Hostile to everything else.

02 · Why that hurts

A POST body is invisible to the web.

A query lives in the request body, so a result set has no identity of its own:

  • No addressable URL — you can't link to “4–5★ hotels in these resorts”; there's no address for it.
  • No caching — POST responses aren't cached by browsers or the edge, so every visitor re‑hits the origin.
  • No sharing or SEO — nothing to bookmark, share, or index.
  • No server‑side rendering — the markup is assembled client‑side after the call, so it can't be previewed or published.

03 · The foundation

One scrape, cached at the edge.

We harvested a whole category from the J2 API and stored the canonical catalogue in a Cloudflare D1 (SQLite) database at the edge — name, brand, image, star rating, reviews, country / area / resort, key selling points.

Now we never call the live booking API at render time. The database is canonical; a refresh re‑flows everything downstream.

04 · The new API

Same data — now a plain GET.

The new worker serialises every filter as a query parameter. The result set finally has an address: it can be linked, cached, bookmarked and shared.

  • Identical JSON shape to the upstream wire format — a drop‑in.
  • Answered from the D1 cache, so it's fast and edge‑cacheable.
GET · JSON

/api/j2/hotels/getcachedhotels

j2api.cpilsworth.workers.dev/api/j2/hotels/getcachedhotels?predefinedResorts=573,575&starRatings=4,5

A /getfilteredhotels proxy also exists for a live, uncached read straight through to the origin.

05 · The HTML rendition

The same URL, rendered to HTML.

A sibling endpoint takes the identical query parameters and returns server‑rendered HTML (a Mustache cards template over the cached data) instead of JSON.

That markup can be dropped straight into a page as a fragment — dynamic hotel listings with no client‑side fetching, no flash of empty content.

GET · HTML

/html/j2/hotels/getcachedhotels

…/html/j2/hotels/getcachedhotels?predefinedResorts=573,575&starRatings=4,5

→ ready‑to‑include <ul class="cards">…

06 · The variation

Clean paths & template‑ready data.

Two refinements make the data publishable, not just embeddable:

DECORATED VIEW

/view/…

JSON pre‑shaped for the template: precomputed star arrays, responsive <picture> srcsets, brand classes — so the renderer does no logic.

PATH‑BASED

/view/…/by-path/{country}/{region}/{resort}

Human URLs like /hotels/portugal/algarve/vilamoura. Stored names are slugified on the fly, so no separate slug column is needed.

TEMPLATE

/templates/cards-page.mustache

Served beside the data by the same worker — so the data shape and its template can never drift out of sync.

07 · Publishing to EDS

JSON→HTML turns data into a real page.

Adobe's helix-json2html worker fetches our view JSON and the template, renders them, and serves HTML. AEM Live previews that as an overlay: it runs the markup through helix-html2md into the content bus and stores it as a normal page.

08 · Two ways to ship the data

Embed it live, or publish it as content.

PATH A · LIVE

Dynamic fragment include

The HTML endpoint is pulled in at request time by the EDS fragment / SSR include. The visitor gets fresh data inserted directly into the page.

Always current · nothing to publish · per‑request.

PATH B · PUBLISHED

JSON→HTML & preview

The data is rendered, previewed and published into EDS as content, then surfaced through linked fragments like any authored page.

Cacheable · indexable · editable as content.

09 · The payoff

What the new layers make available.

  • Addressable result sets — every filter combination is a shareable, cacheable URL.
  • Drop‑in dynamic listings — server‑rendered HTML fragments, no client fetch.
  • On‑demand published pages — hundreds of listing pages without building each one.
  • One canonical source — refresh the cache and both live includes and published pages re‑flow.
  • Data shape & template stay in lockstep — served together, deployed together.
